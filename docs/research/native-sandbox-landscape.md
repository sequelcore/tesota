# Native sandbox landscape (September 2026)

How coding agents confine commands without Docker on Windows, Linux and
macOS, what Microsoft's MXC offers, and what a spike on the operator's
Windows machine showed. Researched on 2026-09-26 from Codex's source at
`c98e263fb5` (2026-09-25), Gemini CLI's at `3818efb`, Microsoft MXC's
repository and `@microsoft/mxc-sdk` 0.8.0, and the
[execution landscape](agent-execution-landscape.md). It continues that page's
"Native OS sandboxes on Windows" section and informs the next execution
decision. Recheck product behavior before relying on it.

## Why it matters

Tesota's sandbox today is Docker Sandboxes, a microVM that needs the Windows
Hypervisor Platform, Docker Sandboxes, a Docker sign-in and a network policy
(`tesota setup`). Without it, every command asks the operator first. For a
user who is not a programmer, both are friction, and approving commands they
cannot judge is also unsafe. Harnesses that are "install and ready" either
sandbox natively or ask per command.

## What harnesses do

| Harness | Linux | macOS | Windows | Default |
| --- | --- | --- | --- | --- |
| Codex (`codex-rs/linux-sandbox`, `windows-sandbox-rs`, `mxc-sandbox`) | bubblewrap: the one on `PATH`, else a `bwrap` bundled with Codex; seccomp network filter; read-only `/` with writable roots; warns when user namespaces are unavailable; WSL1 unsupported | Seatbelt | Two backends. The established one creates sandbox users and group, host ACLs and Windows Filtering Platform rules through an elevated setup. A newer **MXC** backend "never invokes MXC's AppContainer dispatcher, edits host ACLs, creates sandbox users, runs setup, or requests elevation"; it is default-off (`features.prefer_mxc`) | Sandboxed |
| Claude Code (Sandbox Runtime) | bubblewrap and a proxy | Seatbelt | Not supported; WSL2, a container or a VM | Asks per command; sandbox opt-in |
| Gemini CLI (`docs/cli/sandbox.md`) | Docker, Podman, gVisor or LXC | Seatbelt profiles, from "confines writes to the project directory while allowing broad file reads and network access" to strict ones | "Windows Native": sets a Low Mandatory Level on writable paths with `icacls`, a change that persists on the files | Off |

Tesota's earlier checks: the Codex CLI sandbox 0.154.0 failed the
outside-read and network controls (2026-09-13), and Sandbox Runtime on
Windows was not qualified (2026-09-23) ([findings](../findings.md#isolation)).

## Microsoft MXC

[microsoft/mxc](https://github.com/microsoft/mxc), MIT, created 2026-02-06,
"a sandboxed code execution system for running untrusted code (model output,
plugins, tools) on Windows, Linux, and macOS", with a JSON policy schema and a
TypeScript SDK, `@microsoft/mxc-sdk` (0.8.0, published 2026-08-22).

| Platform | Default backend | Requirement |
| --- | --- | --- |
| Windows 11 24H2 or later (build 26100) | `processcontainer`: a BaseContainer through the process security environment when the OS offers it, else an AppContainer whose file policy is added as host ACL entries | None beyond the OS |
| Linux x64 and ARM64 | `bubblewrap` | `bwrap` on `PATH` and unprivileged user namespaces; the enforced proxy-only network mode also needs `slirp4netns`, util-linux, nftables-backed `iptables` and `nf_conntrack` |
| macOS | `seatbelt` | None |

Policies cover files (read-only and read-write paths; denied paths not yet on
Windows), network (egress and ingress default-deny, an HTTP proxy mode; host
allow and block lists "are not implemented on Windows") and, on Windows, UI
access, which is **default-deny** and blocks console tools such as `node` and
`git` from starting unless Win32k is allowed.

**Its status is the limit.** The README: "an early preview", "There are known
cases where the current policies generated by the MXC SDK in this repository
are overly permissive", and "no MXC profiles should be treated as security
boundaries currently". The SDK is "Public Preview" and its schemas may change
before 1.0.

## Spike on the operator's machine

Windows 11 25H2, build 26200; `@microsoft/mxc-sdk` 0.8.0 in a scratch folder,
every binary signed by Microsoft Corporation; a policy with the workspace
read-write, the host's tools and temporary folder from the SDK's helpers,
egress and ingress denied, and Win32k allowed. MXC reported
`isolationTier: "base-container"`. The same results under Node 24.15 and Bun
1.4.2:

| Control | Result |
| --- | --- |
| `node`, `git`, `bun` run inside | Yes, once Win32k is allowed; without it they fail with `0xC0000142` |
| Write inside the workspace | Allowed |
| Write outside it (the user's home) | Denied; no file appears |
| Read `~/.tesota` or the user's Documents | Denied |
| Network, `curl https://example.com` | Refused, DNS included |
| Stop a running command | Stopped at the kill; no process remains |
| Start per command | About 120 to 180 ms |
| Host ACLs | The workspace folder gained no entries of its own |

The machine also carries Codex's `CodexSandboxUsers` group in inherited ACLs
from an earlier Codex setup, so the result needs repeating on a clean
Windows 11. Not yet tested: package-registry access through a proxy, Linux
(bubblewrap), macOS, a clean Windows 11 24H2, and Windows 10, which MXC does
not support.

## Building the provider: what Windows allows

Found on 2026-09-26 while building the `mxc` provider on the same machine,
with `@microsoft/mxc-sdk` 0.8.0.

**Git Bash cannot start in MXC's container.** MSYS2's `bash.exe`, launcher or
not, exits with 66 before any output, with a valid environment and even with
Git's folder writable. Windows PowerShell 5.1, installed with Windows, runs;
PowerShell 7 was not installed. Codex's shell on Windows is PowerShell too
(`shell-command/src/shell_detect.rs`).

**An explicit environment needs `SYSTEMROOT` and `LOCALAPPDATA`.** Without
them the launch fails with Windows error 203; Windows only checks that they
exist, and MXC's main branch now validates them before launch (issues 1130
and 1102, commit `491ac954`). Without an explicit environment, the command
receives the operator's own Windows user environment, `APPDATA` included.

**Tools cannot walk above the workspace.** In MXC's BaseContainer a process
cannot query the workspace's parent folders. Tools that resolve a path by
walking from the drive root fail: `node script.cjs` (Node's JavaScript
`realpath` stops at `lstat C:\`), `npm`, whose entry file sits under
`C:\Program Files`, and Git ("unable to get current working directory:
Permission denied"); Bun ran scripts. MXC documents this as "Upward directory
traversal for Windows BaseContainer". Granting `C:\` through the SDK was no
way out: the command then read the operator's `~/.tesota` and listed their
home folder.

**MXC's intended fix is not on released Windows.**
`processContainer.filesystem.enumeratePaths`, added on 2026-09-16
([issue 1162](https://github.com/microsoft/mxc/issues/1162)), lets a command
query and list folders "without granting file content reads". It needs
schema `0.9.0-alpha`, not in any npm release yet, and Windows' process
security environment 1.1 with `fs_enumerate`: MXC's support matrix marks it
unavailable on 23H2, 24H2 and 25H2, possible only on builds from 26600, and
validated on Insider builds 26657 and 26663; without it MXC fails rather than
broaden access. Microsoft documents this API only through MXC.

**How the labs meet it.** GitHub Copilot's local sandbox is built on MXC, the
BaseContainer tier on Windows, and "Local sandboxing on Windows requires a
Windows Insiders build"; its default also lets commands read package
managers' configuration "and the tokens they store", with the network open
([configuring local sandbox settings](https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes/configuring-local-sandbox-settings)).
Codex's policy reads the whole disk, so it never meets the limit and does not
use `enumeratePaths`. Claude Code has no native Windows sandbox. No lab offers
confined reads on released Windows 11.

**A drive rooted at the workspace works today.** `subst T: <workspace>` needs
no administrator rights, and with the command's folder on `T:\` there is no
parent to walk: Git and `node script.cjs` ran, and `npm install` fetched a
package through Tesota's proxy with Node's `--preserve-symlinks` and
`--preserve-symlinks-main` flags, which spare npm from walking its own
install folder. The grant must name the real folder, not the drive, and the
drive must be the workspace itself: a drive over a parent folder failed the
same way. Home, temporary and cache folders at ordinary paths were fine for
Git, Node and npm. `bun install` still failed with `ENOENT` before any
download, with every Bun directory variable tried, so it is left to the
per-command retry on this computer until `fs_enumerate` ships.

**Certificate revocation.** Windows' own TLS, used by `curl.exe` and by Git
configured with `schannel` as on this machine, checks revocation online and
failed with `CRYPT_E_REVOCATION_OFFLINE`, since the revocation servers are
not on the allowlist; npm and Bun use their own TLS. MXC tracks related work
for proxies ([issue 1262](https://github.com/microsoft/mxc/issues/1262)).

## Implications for Tesota

1. **A native provider can meet the friction goal on Windows today**: no
   install beyond Tesota, no elevation, and the same four controls Docker
   Sandboxes passes, on the machine tested.
2. **MXC covers all three systems behind one TypeScript SDK**, which suits
   Tesota's stack and its provider interface; Codex's own adoption, although
   default-off, is independent corroboration.
3. **It cannot be called a security boundary yet**, by Microsoft's own
   statement. Tesota may claim only what its live controls show, per host, and
   must say that the backend is a preview; Docker Sandboxes stays the strong
   boundary for those who have it.
4. **Linux needs `bwrap`, and enforced network rules need more tools.**
   Codex bundles a `bwrap` for hosts without one; whether Tesota should, and
   how Ubuntu's restriction of unprivileged user namespaces affects it, needs a
   test on a real Linux host.
5. **The network allowlist is the open question:** Docker Sandboxes allows
   package registries through its proxy; the native equivalent is MXC's proxy
   mode on Windows and Linux, and cooperative on macOS, which the spike has not
   yet tested.
6. **Fallback for everyone else:** Windows 10 and hosts that fail the probe
   keep Docker Sandboxes or asking per command, and should say which applies.
7. **Commands run in PowerShell 5.1** in the native Windows sandbox, as in
   Codex, since Git Bash cannot start there; Docker Sandboxes and this
   computer keep bash.
8. **Keep reads confined on released Windows with a drive rooted at the
   workspace,** the only way found that keeps the operator's files
   unreadable and lets Git, Node and npm work; move to `enumeratePaths`,
   which keeps real paths, once the SDK exposes it and qualification finds
   the host reports `fs_enumerate`. Reading the whole disk, as Codex does,
   would give up the guarantee that sets Tesota apart.
