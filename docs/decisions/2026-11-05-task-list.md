# Keep task progress in the engine session

**Status:** Proposed; design only, product acceptance pending.
**Date:** 2026-11-05. **Owner:** Tesota's operator.
**Work:** [#521](https://github.com/sequelcore/tesota/issues/521).

## Context

Long requests need visible progress and exact list restoration after context
compaction. Task completion is an agent claim, separate from request scope,
verification evidence, and human acceptance. The engine already owns an
append-only session log, request continuation links, sequential native tool
calls, terminal drawing, and mandatory verification.

## Proposed decision

Add one full-list replacement tool and persist successful structured results in
the existing session log. One engine policy owns validation and projection for
live execution, replay, context restoration, and terminal display. Extend current
owners directly; alpha requires no compatibility layer or alternate store.

Bind lists to recorded request lineage. Reopening a session displays saved state
without restarting work. An explicit continuation inherits its list; an unlinked
new request starts empty. Generic continuation after a stopped run remains a
product decision, not a semantic guess by the task tool.

Derive the state a compaction restores from the journal entries before it, so
the session format and compaction entries stay unchanged, and include that
state in context and token accounting. Keep summary decisions and
evidence, and preserve the original request ledger's authority. At admission,
record a derived lineage-and-state notice before the request sync, outside
operator input. Draw a compact task row with Ctrl+O expansion, separately from
questions and verification.

Propose default-off availability and ordinary permission handling with no
workspace effects. Defer stable IDs, deletion rejection, shared task graphs,
periodic reminders, receipt changes, and child task tools. The
[design](2026-11-05-task-list-design.md) owns the proposed bounds, recovery
rules, alternatives, tests, and rollout experiment.

## Consequences

Full replacement gives deterministic state with little tool surface, but can
omit items and loses per-item identity. Recorded snapshots retain history;
they do not establish that every requirement was completed. Each accepted
update adds a sync and session data. Restoration adds bounded context.
Existing sessions open unchanged. A build without the feature opens sessions
that hold lists, shows task calls as ordinary history, and restores no task
section after compaction.

No task state bypasses permissions, verification, settlement, or acceptance.
Existing sequential execution removes the need for a new task-update queue.
Implementation checks must establish mechanics; usability and overhead need
measurement before the owner chooses default adoption.

## Limits of this decision

Changing settings cannot alter replay: restoration follows the journal alone.
Admission notices follow all admission messages, before their sync. Existing
reference and check-plan ordering is outside this feature; task ordering must
agree live and on replay.

The design was checked against source excerpts and establishes no implemented
behavior. Fault injection, provider-context checks, and real terminal evidence
remain required. Full replacement still permits omitted items and costs
context; the proposed trial compares this with ordinary progress messages
before default adoption.

## Unresolved owner decisions

Request-lineage scope and stopped-work continuation; default-off rollout; payload bounds; read-mode access; primary-focus semantics
and item omission;
paid trial budget and acceptable overhead. Review this decision when a real
consumer needs human item editing, shared ownership, or cross-session tasks.
