# Practical-use pilot: observed results

This record follows the [frozen protocol](2026-09-22-pilot.md). It is a
diagnostic-only result, not evidence that either system can complete general
repository tasks. The comparator's local shell helper was unavailable on both
attempts, so no controlled coding-capability conclusion is supported.

## Preconditions

The Gentle AI, Gentle Pi and Pi clones were fast-forwarded to their then-current
`main` commits before selection; tgrep was cloned at its selected commit. All
four original clones were clean before and after the pilot. Tesota updated its
four pinned Pi packages from `0.86.1` to `0.87.1` to use the published
`gpt-6-luna` Codex model. `bun run check` passed on Windows (500 tests, typecheck,
build and lint). A separate two-invocation live route smoke passed: one
completed response and one observed cancellation, both HTTP 200, with no
repository tools. The [sanitized v9 route record](../codex/evidence/gpt6-luna-route-2026-09-22.json)
binds the observed source and build; it was not used as task-success evidence.

## Decision from this pilot

The read-only overlap case shows a useful Tesota answer on this one repository.
The source-and-test case remains unmeasured: Tesota's discovery failed before
its known scope boundary, and the comparator's shell failed independently.
The immediate repair is to expose a safe, bounded discovery failure cause and
requalify the comparator's local tool setup on a non-task fixture before any
fresh comparison. Do not call either failure a model deficiency or silently
replace these attempts. A later task set must include an admitted source change
and fresh work if the roadmap's practical-use baseline is to be established.

## Subsequent infrastructure diagnosis (not a pilot retry)

The Codex CLI sandbox log identified a runtime read/execute validation failure:
Windows `CreateFileW` could not open one directory in Codex's own cached
`cua_node` runtime during elevated setup. This happened before repository
commands and independently of the Notion MCP OAuth refresh warning. The local
directory existed when checked; the log did not identify the underlying Windows
error, so path length and permissions remain possible explanations rather than
established causes. An isolated, no-model `codex sandbox` command failed in the
configured `elevated` mode and succeeded with a per-command `unelevated`
override. No global Codex setting or runtime cache was changed. The installed
CLI's sandbox command takes the command directly, despite the newer official
documentation showing a `windows` subcommand. OpenAI documents `unelevated` as
a weaker temporary fallback, not a security-equivalent replacement for
`elevated`; any later comparison must disclose the changed sandbox condition.

Tesota now reports an allowlisted discovery tool and failure category without
retaining model arguments, paths or raw exceptions. Synthetic SDK tests cover
denied reads, missing evidence, unavailable tools and unexpected backend errors.
This does not reconstruct the failed Gentle Pi model call: the original shell
did not retain it. These changes and infrastructure probes do not replace or
rescore any of the four frozen attempts above.

After the repair passed `bun run check`, a separate Codex CLI agent diagnostic
used the per-command `unelevated` fallback and requested only `git rev-parse
HEAD` in tgrep. Its shell tool executed successfully (exit 0) and returned the
selected baseline. A Notion OAuth refresh warning still appeared but did not
prevent this local command. This qualifies one read-only agent/tool invocation,
not a coding attempt or the stronger sandbox mode.

A separate Tesota reproduction used the original Gentle Pi request in the
ordinary shell. This time discovery did not fail: after about 93 seconds it
retained a non-authoritative proposal to edit `lib/openspec-deltas.ts` and
`tests/openspec-deltas.test.ts`. Those paths are outside the current supported
`src/` source-only admission, so the shell stopped at task start with no
candidate, approval, check or source edit. The original clone remained clean.
The first tool failure was therefore not reproduced; its exact cause remains
unknown. This new observation exposes the expected coverage boundary, but it
must not be counted as a replacement pilot attempt.

A further one-attempt Codex CLI diagnostic used the same Gentle Pi request in

## Subsequent ordinary-shell source-and-test attempt

One ordinary Tesota Shell attempt then used the original Gentle Pi request and
`gpt-6-luna` against the clean original clone. Repository discovery reached its
120-second deadline and ended with `Repository discovery timed out after
confirmed settlement. Start a new request. Nothing changed.` It produced no
proposal, candidate, source or test edit, Docker check, or review decision. The
cause of the slow discovery was not established; a full local verification was
running concurrently, so this observation cannot be attributed to the model or
the new task contract. This is not a retry or replacement of the frozen pilot,
and it does not qualify the integrated source-and-test conversation.

## Discovery latency and proposal-shape follow-up (not a pilot retry)

An isolated run of the same continuous Pi discovery owner against the clean
Gentle Pi baseline completed a source-and-test proposal in 59.2 seconds, using
8 model invocations, 9 tool calls and 9 repository operations (46,179 bytes
exposed). No task execution was requested. An ordinary Shell run on the same
baseline reached a proposal in about 70 seconds, using 9 model invocations,
10 tool calls and 10 operations (47,155 bytes exposed). Thus the earlier
120-second timeout did not reproduce in these two attempts; its cause remains
unidentified, and a longer deadline is not justified by these observations.

The Shell proposal was not executable: it requested `scope-integrity`,
`typescript-no-emit/v1` and `node-test-targeted/v1` together. The current
source-and-test grant allows only the first and third. The record was marked
`ready` because retention previously checked dirty paths but not supported
scope, so the Shell displayed an approval handoff before admission rejected
it. No candidate, Docker check, decision or source edit occurred; the original
clone stayed clean. A narrow follow-up now previews the same supported shape
used by admission, labels incompatible proposals `blocked_scope`, and tells
the model to choose exactly the admitted check pair. Admission still rechecks
the source and policy; this prompt change is not an authorization mechanism.

A subsequent ordinary Shell attempt after that prompt and structural-preview
change still requested all three checks. The new record was correctly marked
`blocked_scope` and the Shell stopped before approval; it took about 74 seconds
and made 9 model calls and 9 tool calls. The original clone stayed clean. This
shows that clearer prompt text alone did not remove the practical obstacle.
One further bounded experiment returned the exact supported check pair to the
model after its first incompatible submission. A deterministic SDK test could
complete after a corrected second submission, but the ordinary live Shell
reached its model-invocation limit after about 78 seconds without any proposal.
The feedback path was removed rather than increasing budgets or retaining an
unhelpful second protocol. The structural `blocked_scope` result and prompt
clarification remain; neither makes the current model reliably propose this
task. No candidate or original-repository edit occurred in any follow-up.
